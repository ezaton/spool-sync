## Critical Issues

### 1. URL mismatch will cause double `/api/v1` (Section 3.2.3)

The integration passes `cfg.spoolman_url` to `run_migration()`:

```python
run_migration(base_url=cfg.spoolman_url, ...)
```

But `cfg.spoolman_url` includes the `/api/v1` suffix:

```python
# config.py line 39
spoolman_url: str  # e.g. http://spoolman:8000/api/v1
```

And the migration script builds paths WITH the `/api/v1` prefix:

```python
# migrate_variant.py
resp = http.get("/api/v1/filament")             # line 150
resp = http.patch(f"/api/v1/filament/{fid}")    # line 185
```

**Result:** Requests to `http://spoolman:8000/api/v1/api/v1/filament` -- 404 at runtime.

Same Section 3.2.4 (one-way mode) has the identical issue.

**Fix options:**

- (a) Strip `/api/v1` before passing: `cfg.spoolman_url.removesuffix("/api/v1")`
- (b) Refactor migration to use paths without `/api/v1` prefix (matching
  `SpoolmanClient` convention)
- (c) Refactor migration to accept a `SpoolmanClient` instance instead of a raw URL

Note: This same class of bug (double `/api/v1` in docker compose migration
commands) was caught and fixed during design-review-v2 of the variant sync design.

### 2. Contradictory websocket timing (Sections 2, 3.2.3, 3.3, 4.2, 7)

The document contradicts itself on whether the websocket listener runs during
migration:

| Section | Claim | Websocket active? |
|---------|-------|-------------------|
| 2 (startup diagram) | Migration step 4, websocket step 5 | No |
| 2 (text) | "websocket listener is **already running**" | Yes |
| 3.2.3 (code) | Migration before `_startup_sequence()` | No |
| 3.3 (first paragraph) | "websocket listener is **not yet started**" | No |
| 3.3 (alternative) | Proposes restructure to start WS first | Implies currently no |
| 4.2 | "listener starts before migration" | Yes |
| 7 (summary) | "Active (listener starts before migration)" | Yes |

The proposed code in Section 3.2.3 is authoritative: migration runs BEFORE
`_startup_sequence()`, so the websocket is NOT active during migration.

Sections 2 (text), 4.2, and 7 make the opposite claim.

**Fix:** Either:
- (a) Adopt the restructured sequence from Section 3.3 (start websocket before
  migration) and remove the contradictory claims, OR
- (b) Keep migration before startup and correct Sections 2, 4.2, and 7 to
  state the websocket is not yet active

Either way is fine -- the migration only writes to Spoolman (no websocket events
are generated by filament PATCH), so websocket timing doesn't affect correctness.
But the document must be internally consistent.

## Incorrect Claim

### 3. "Matching the bridge's behavior" is false (Section 3.1)

Section 3.1 states the merge fix will match "the bridge's behavior." The actual
bridge code at `spoolman.py:119-121`:

```python
if spec.extra:
    body["extra"] = spec.extra
```

This is a **full replacement**, not a merge. The bridge does NOT read the existing
filament's `extra` from `existing[0]` and merge. The bridge has the same latent
bug at two sites:

| Call site | Code | Behavior |
|-----------|------|----------|
| `upsert_filament()` (spoolman.py:120-121) | `body["extra"] = spec.extra` | Full replacement |
| `upsert_spool()` (spoolman.py:162) | `"extra": spec.extra` | Full replacement |

The proposed migration fix is correct on its own merits (the migration has the
existing filament data available in `f`), but the stated rationale is wrong.

**Recommendation:** Either fix the bridge too (read `existing[0].get("extra", {})`
and merge in `upsert_filament`), or drop the "matching the bridge" claim and
note that the bridge has the same latent issue.

## Unverified Assumption

### 4. Spoolman PATCH behavior for `extra` (Section 2)

The document states: "the Spoolman API's PATCH endpoint replaces the entire
`extra` dict." This is the foundational assumption for the bug. No verification
method is cited (Spoolman source code, API docs, or empirical test).

If Spoolman actually **merges** `extra` on PATCH (sending
`{"extra": {"variant": "..."}}` adds/updates just the `variant` key), then
neither the migration nor the bridge has this bug.

**Recommendation:** Verify empirically before implementing:

```bash
# Create a filament with two extra fields, then PATCH with one
curl -X PATCH http://spoolman:8000/api/v1/filament/<id> \
  -H 'Content-Type: application/json' \
  -d '{"extra": {"test_field": "\"value\""}}'
# Check if the original extra fields survived
curl http://spoolman:8000/api/v1/filament/<id> | jq .extra
```

## Minor Issues

### 5. `run_migration()` wrapper adds no value (Section 3.2.2)

```python
def run_migration(base_url, dry_run=False, filament_id=None):
    return migrate_filaments(base_url, dry_run=dry_run, filament_id=filament_id)
```

Identical signature, pure pass-through. The integration can call
`migrate_filaments()` directly. The wrapper adds an unnecessary layer of
indirection.

### 6. Proposed unit test is trivial (Section 5.1)

The test validates Python's `{**a, **b}` dict merge syntax, not actual migration
code. A meaningful test would:

- Mock `httpx.Client` to return a filament with pre-existing extra fields
- Call `migrate_filaments()` with the mock
- Assert the PATCH body merges (not replaces) the extra dict
