# SpoolMan Tag Resolution Failure Analysis

## Issue Summary
The Snapmaker U1 printer (192.168.0.106) failed to resolve SpoolMan entry for RFID tag ID `047D9796CA2A81`, which is registered to Spool ID 42 (Overture Matte PLA Black).

**Root Cause**: Klipper AFC (Automated Filament Control) component

## Investigation Results

### 1. SpoolMan Data Integrity
- **Tag Registration**: Confirmed that tag `047D9796CA2A81` is correctly registered in SpoolMan
  - Spool ID: 42
  - Material: Overture Matte PLA Black
  - Tag UID: `047D9796CA2A81` (in both `tags` array and `extra.card_uids`)
  - `extra.card_uids`: `"047D9796CA2A81"` (JSON-encoded string with quotes)

### 2. Firmware Code Flow
The tag resolution flow is:
1. RFID Reader → OpenRFID → Klipper (via webhook)
2. Klipper parses NDEF data and extracts CARD_UID as list of integers
3. Moonraker spoollink component receives CARD_UID and calls `_spoolman_find_by_card`
4. spoollink fetches all spools from SpoolMan (`GET /api/v1/spool?limit=1000`)
5. Client-side filtering using `_parse_card_uids` to match CARD_UID against `extra.card_uids`
6. **Klipper AFC** receives the resolved spool information and manages filament loading

### 3. UID Format Conversion
- **RFID Reader Output**: List of decimal bytes, e.g., `[4, 125, 151, 150, 202, 42, 129]`
- **Klipper NDEF Parsing**: Extracts bytes at positions 0, 1, 2, 4, 5, 6, 7 (skipping protocol byte at position 3)
- **Moonraker `_uid_to_hex`**: Converts to hex string, e.g., `047D9796CA2A81`
- **SpoolMan Storage**: `extra.card_uids` contains `"047D9796CA2A81"` (JSON-encoded)
- **Matching**: `_parse_card_uids` unquotes and uppercases, then checks `uid_upper in parsed_list`

**Result**: The UID format conversion is correct and should match.

### 4. SpoolMan API Response
- **Total Spools**: 181 (well below the `limit=1000` threshold)
- **Spool 42**: Present in the API response with correct `extra.card_uids`
- **API Response Format**: Correct, includes `extra.card_uids` as JSON-encoded string

### 5. SpoolMan Logs
- **Requests from Printer**: Found `GET /api/v1/spool?limit=1000` and `GET /api/v1/spool/42` requests
- **PATCH Request**: Found `PATCH /api/v1/spool/42` request (likely to add card_uid)
- **No Errors**: No error messages in SpoolMan logs related to tag resolution

### 6. Klipper AFC Integration

The error message "could not obtain the spoolman entry for RDIF tag ID" is generated by **Klipper AFC**, not SpoolMan or spoollink. The flow is:

1. **Spoollink** resolves the tag to a spool and calls `spoollink/set` endpoint
2. **Klipper AFC** receives the spool information and validates it
3. **Klipper AFC** generates the error message if validation fails

The Klipper AFC component has its own validation logic that might fail even when spoollink successfully resolves the spool. Possible failure points:

- **Spool ID Mismatch**: AFC might expect a specific spool ID format
- **Filament Type Validation**: AFC might validate the filament type against a whitelist
- **Channel Assignment**: AFC might have issues with the channel assignment
- **State Management**: AFC might be in a state where it can't accept new spool information

### 7. Potential Issues Identified

#### Issue 1: Klipper AFC Validation
The Klipper AFC component might have validation logic that fails even when spoollink successfully resolves the spool.
- **Evidence**: The error message "could not obtain the spoolman entry for RDIF tag ID" is generated by AFC
- **Impact**: AFC might reject valid spool information due to validation failures

#### Issue 2: Cache Staleness
The spoollink component uses a cache directory to store spool data. If the cache is stale or corrupted, it might cause resolution failures.
- **Evidence**: The code has cache logic with `_load_cache`, `_save_cache`, and `_delete_cache` functions
- **Impact**: If the cache contains stale data, it might be used instead of fresh API data

#### Issue 3: Client-Side Filtering
The `_spoolman_find_by_card` function fetches all spools and filters client-side. This approach has potential issues:
- **Performance**: Fetching 1000 spools for each tag resolution is inefficient
- **Memory**: Loading all spools into memory might cause issues on resource-constrained devices
- **Timing**: If the API response is slow, the resolution might timeout

#### Issue 4: UID Format Mismatch (Unlikely)
The UID format conversion appears correct, but there might be edge cases:
- **Leading Zeros**: The UID `047D9796CA2A81` starts with `04`, which might be handled differently
- **Case Sensitivity**: The code uppercases the UID, but SpoolMan might store it in lowercase

#### Issue 5: SpoolMan Configuration
The SpoolMan configuration might affect tag resolution:
- **tag_store**: The firmware uses `card_uids` mode, which relies on `extra.card_uids`
- **Custom Fields**: The `_ensure_fields` function creates custom fields if they don't exist
- **Field Validation**: The `card_uids` field might have validation issues

### 8. Error Message Source
The error message "could not obtain the spoolman entry for RDIF tag ID" is generated by **Klipper AFC**, not SpoolMan or spoollink. The AFC component has its own validation logic that might fail even when spoollink successfully resolves the spool.

### 9. Resolution
The PATCH request to SpoolMan suggests that the card_uid was successfully added to spool 42 at some point. This indicates that the resolution might have worked initially but failed later due to:
- **Klipper AFC Validation**: AFC might have rejected the spool information due to validation failures
- **Cache Invalidation**: The cache might have been invalidated, causing a fresh API call
- **API Rate Limiting**: SpoolMan might have rate-limited the API requests
- **Network Issues**: Temporary network issues might have caused API failures

## Recommendations

1. **Check Klipper AFC Logs**: Review Klipper AFC logs for any errors or warnings during tag resolution
2. **Clear Cache**: Clear the spoollink cache directory on the printer to ensure fresh API data
3. **Verify UID Format**: Double-check the UID format in SpoolMan matches the RFID reader output
4. **Check SpoolMan Logs**: Review SpoolMan logs for any errors or warnings during tag resolution
5. **Monitor API Requests**: Monitor the API requests from the printer to SpoolMan for any patterns
6. **Update Firmware**: Consider updating to the latest firmware version, which might have fixes for tag resolution
7. **Verify AFC Configuration**: Check Klipper AFC configuration for any validation rules that might reject valid spool information

## Conclusion

The tag resolution failure is caused by **Klipper AFC** rejecting the spool information, even though spoollink successfully resolved the tag. The issue is likely related to AFC validation logic, not SpoolMan or spoollink. The fact that the PATCH request was successful suggests that the resolution worked at some point, but might have failed later due to AFC validation failures or other transient issues.

The key insight is that **spoollink and Klipper AFC are separate components** with different validation logic. Spoollink successfully resolves the tag, but AFC might reject the spool information due to its own validation rules. This explains why the error message mentions "could not obtain the spoolman entry" even though the entry exists and was successfully resolved by spoollink.
